# TanStack Start Migration Sketch

A pragmatic migration plan for moving Paper Trail from a Vite SPA + standalone Hono Worker to [TanStack Start](https://tanstack.com/start) running on Cloudflare Workers.

> **Status:** Exploratory sketch, not a committed plan. TanStack Start is pre-1.0 — APIs may shift.
>
> **Notes when reading this doc:**
> - Auth has moved from Cloudflare Access (email header) to Clerk
>   (`Authorization: Bearer <JWT>`). See `docs/CLERK_AUTH.md`.
> - Stripe has been removed. Invoices are self-hosted, rendered from a
>   frozen snapshot, and delivered via Resend; customers pay
>   out-of-band via Venmo/PayPal deep links. Anywhere this doc mentions
>   "Stripe webhooks" or `api/src/routes/stripe.ts`, substitute "the
>   public hosted-invoice + consent routes" (`api/src/routes/publicInvoice.ts`,
>   `api/src/routes/consent.ts`).

## Why TanStack Start

- Already use TanStack Query → matches the ecosystem.
- Vite-based → keeps current build tooling.
- Official Cloudflare Workers support via `@cloudflare/vite-plugin`.
- File-based routing replaces the current Zustand `activeTab` switch.
- Server functions can replace most of the `api/` Hono routes incrementally.
- Type-safe loaders/links across the client/server boundary.

## Why not the alternatives

- **Next.js** — too heavy, ties you to Vercel-isms, awkward on Workers.
- **React Router v7 framework mode** — solid choice, but you don't already use it; TanStack Start gives you more leverage from existing investments.
- **Waku** — too young for a production app handling money.

## What stays the same

- Cloudflare D1, R2, Access (GitHub OAuth), Wrangler secrets.
- React 19, Zod, date-fns, CSS Modules, Biome, Vitest.
- Database schema and migrations in `api/db/migrations/`.
- Domain logic in `src/app/components/features/*` — components don't move.
- Stripe integration code in `api/src/routes/stripe.ts` (becomes a server function module).

## What changes

| Today | After |
| --- | --- |
| `src/app/index.tsx` switch on `activeTab` | `src/routes/*` file-based routes |
| `src/app/lib/store.ts` `activeTab` + `changeActiveTab` | URL is the source of truth; route params/search params replace tab state |
| `src/app/lib/db/client.ts` (fetch wrapper) | Server functions called directly from components |
| `api/src/routes/*.ts` (Hono handlers) | Server functions colocated with routes (or kept as a Hono app mounted under `/api`) |
| `src/app/components/shared/ModalRenderer` | Modal routes (e.g. `/customers/$customerId/edit`) — optional |
| Manual React Query setup | TanStack Start ships with Query integration |

## High-level architecture

```
src/
├── routes/                    # File-based routes (replaces activeTab switch)
│   ├── __root.tsx             # Layout + Nav + ModalRenderer
│   ├── index.tsx              # Redirect → /timesheets
│   ├── timesheets.tsx
│   ├── transactions.tsx
│   ├── invoices.tsx
│   ├── customers.tsx
│   └── settings.tsx
├── server/                    # Server functions (createServerFn)
│   ├── customers.ts
│   ├── invoices.ts
│   ├── stripe.ts
│   └── ...
├── app/
│   ├── components/            # Unchanged
│   └── lib/
│       ├── store.ts           # Slimmed: only modal state, theme moves to a route loader or cookie
│       └── db/                # Removed or shrunk — server functions replace the fetch wrapper
└── routeTree.gen.ts           # Generated by TanStack Router

api/                           # Optional: keep for /invoice/*, /consent/* public endpoints
└── src/
    ├── index.ts               # Hono app, mounted in routes/api.$.ts via fetch handler
    └── lib/                   # auth middleware, db helpers stay
```

## Step-by-step migration

### 1. Install and configure

```bash
pnpm add @tanstack/react-start @tanstack/react-router
pnpm add -D @tanstack/router-plugin @tanstack/router-devtools
```

Update `vite.config.ts`:

```typescript
import { defineConfig } from "vite";
import { tanstackStart } from "@tanstack/react-start/plugin/vite";
import { cloudflare } from "@cloudflare/vite-plugin";
import viteReact from "@vitejs/plugin-react";

export default defineConfig({
  resolve: { tsconfigPaths: true },
  plugins: [
    cloudflare({ viteEnvironment: { name: "ssr" } }),
    tanstackStart(),
    viteReact(),
  ],
});
```

Update `package.json` scripts:

```json
{
  "scripts": {
    "dev": "vite dev",
    "build": "vite build && tsc --noEmit",
    "preview": "vite preview",
    "deploy": "pnpm run build && wrangler deploy",
    "cf-typegen": "wrangler types"
  }
}
```

`wrangler.jsonc` stays mostly the same — D1/R2 bindings unchanged. The `assets` block is updated by the Start build output (no more `dist/` SPA fallback; the Worker becomes the entry point and serves the built assets).

### 2. Create the root route

`src/routes/__root.tsx`:

```tsx
import { createRootRoute, Outlet } from "@tanstack/react-router";
import { Nav } from "@/components/layout/Nav";
import { PageWrapper } from "@/components/layout/PageWrapper";
import { ModalRenderer } from "@/components/shared/ModalRenderer";

export const Route = createRootRoute({
  component: () => (
    <PageWrapper>
      <Nav />
      <Outlet />
      <ModalRenderer />
    </PageWrapper>
  ),
});
```

### 3. Convert tabs to routes

Each current page becomes one route file. Example — `src/routes/customers.tsx`:

```tsx
import { createFileRoute } from "@tanstack/react-router";
import { Customers } from "@/Customers";
import { getCustomers } from "@/server/customers";

export const Route = createFileRoute("/customers")({
  loader: () => getCustomers(),
  component: Customers,
});
```

The existing `Customers` component stays — it just reads loader data instead of calling `useQuery({ queryFn: getCustomers })`. (Or keep `useQuery` and let Start's Query integration hydrate it from the loader — both work.)

### 4. Update the Nav component

Replace `changeActiveTab` calls with `<Link>`:

```tsx
import { Link } from "@tanstack/react-router";

<Link to="/customers" className={styles.navButton} activeProps={{ className: styles.navButtonActive }}>
  <Users size={40} />
</Link>
```

Drop `activeTab` and `changeActiveTab` from `usePaperTrailStore`.

### 5. Convert API routes to server functions (incremental)

A current Hono route like `getCustomers` in `api/src/routes/customers.ts` becomes:

```typescript
// src/server/customers.ts
import { createServerFn } from "@tanstack/react-start";
import { getDb } from "@/server/lib/db";
import { requireUserId } from "@/server/lib/auth";

export const getCustomers = createServerFn({ method: "GET" }).handler(async () => {
  const userId = await requireUserId();
  const db = getDb();
  const { results } = await db
    .prepare("SELECT * FROM customers WHERE userId = ?")
    .bind(userId)
    .all();
  return results;
});
```

Frontend import changes from `@/lib/db/customers` → `@/server/customers`. Call signatures stay the same. The fetch wrapper in `src/app/lib/db/client.ts` can be deleted once all routes are converted.

**Cloudflare bindings inside server functions:** access via `getRequestEvent().context.cloudflare.env` (Workers env is injected by the Cloudflare Vite plugin). Wrap this in a `getEnv()` helper to mirror the current `getDb(c.env)` pattern.

### 6. Keep public endpoints as Hono (optional)

`/invoice/*` and `/consent/*` are unauthenticated public-facing endpoints that don't fit the server-function model (they receive Stripe webhooks / customer-facing links). Keep the existing Hono app and mount it as a catch-all route:

```tsx
// src/routes/api/$.tsx — or use a custom request handler
import { createFileRoute } from "@tanstack/react-router";
import { honoApp } from "@/server/hono"; // existing api/src/index.ts moved here

export const Route = createFileRoute("/api/$")({
  server: {
    handlers: {
      GET: ({ request }) => honoApp.fetch(request),
      POST: ({ request }) => honoApp.fetch(request),
      // ...
    },
  },
});
```

### 7. Auth middleware

Cloudflare Access still injects the `Cf-Access-Authenticated-User-Email` header. Move the existing `api/src/middleware/auth.ts` logic into a server-function helper (`requireUserId()`) that reads the header from `getRequestEvent().request.headers` and auto-creates the user on first call. Same code, different invocation site.

### 8. Modals as routes (optional, future)

Currently modals are driven by Zustand (`activeModal`). They could become URL-driven using parallel routes or modal route patterns:

- `/customers` — list
- `/customers/$customerId` — view (modal layer)
- `/customers/new` — create (modal layer)

Benefit: deep-linkable, browser back closes modal, no global modal state. Defer this until the basic migration is stable — it's a UX change, not a tech change.

## Migration order (suggested)

1. Install Start, get `vite dev` running with an empty `__root.tsx` and a single redirect route.
2. Add one route (`/customers`) end-to-end with a server function — prove the pattern works on Workers locally.
3. Convert remaining tabs to routes one at a time. Keep `usePaperTrailStore.activeTab` working in parallel until all are done.
4. Convert `api/src/routes/*` to server functions one feature at a time. Old Hono routes keep working — the frontend just stops calling them.
5. Once all internal API routes are server functions, delete `src/app/lib/db/client.ts` and the corresponding Hono routes.
6. Keep `/invoice/*`, `/consent/*`, Stripe webhooks as Hono mounted under `/api/$`.
7. Delete `activeTab` from the store.
8. (Optional) Convert modals to routes.

Each step ships independently. No big-bang cutover.

## Risks and unknowns

- **Pre-1.0 churn** — APIs may change between releases. Pin versions, watch the changelog.
- **Cloudflare Access header forwarding** — verify the header reaches server functions in the Vite dev environment (it does today via the Hono middleware; need to confirm the path through Start).
- **R2 streaming** — file upload/download in `api/src/routes/files.ts` uses streaming. Server functions support streaming responses but the ergonomics differ; may want to keep file routes as Hono.
- **Vitest** — Start has its own test setup conventions. Existing `*.test.tsx` files should still work since they test components in isolation, but route-level tests will need new patterns.
- **SSR** — Start defaults to SSR. For an authenticated dashboard behind Cloudflare Access this is wasted work; configure routes as `ssr: false` or use the SPA mode where appropriate.
- **Bundle size** — Start adds the Router + server-fn runtime. Measure before/after.

## Effort estimate

Rough order-of-magnitude, assuming one engineer familiar with the codebase:

- Setup + first route working: **half a day**.
- Convert all 5 tab routes: **1 day**.
- Convert API routes to server functions: **2–3 days** (8 route files, mechanical work).
- Cleanup + removing the fetch wrapper + store changes: **half a day**.
- **Total: ~1 week** of focused work, shippable incrementally.

## Decision checklist before starting

- [ ] Are we OK with a pre-1.0 framework dependency?
- [ ] Do we want URL-driven navigation badly enough to justify the migration?
- [ ] Is there a near-term feature (deep linking, SSR for SEO, server-rendered invoice pages) that needs this?
- [ ] Have we confirmed Cloudflare Access flows work end-to-end in a Start prototype?

If three of four are "no," stay on the current SPA. The current setup is small and works.
